# Prototype workflow

기획 요청 → 기획 → 제작단계 제안 → 제작 → 리뷰 → 문서로 증명의 순서를 준비하고, 사용자가 식별된 프로젝트의 시작을 결정하면 실행한다. 목적은 요청이 실행 가능한 결과물로 이어지는 과정과 생산성을 보여주는 것이다. 오류 수정 사례만을 AI 활용의 대표 성과로 삼지 않는다.

사용자용 설명은 [GUIDE.md](GUIDE.md), 시작 절차와 검토표는 [startup-flow.md](references/startup-flow.md)에 있다. 처음 적용할 때 두 문서를 읽고 현재 모드를 판별한다.

에이전트를 배정하기 전에 [모델·Effort 정책](references/model-routing.md)을 읽는다. 이 프로젝트는 Main Context만 Astra · Ultra, 보조는 Luna · Low / Terra · Medium / Sol · High를 사용한다. 배정 시 모델과 Effort를 모두 명시하고 전체 대화 상속을 기본값으로 쓰지 않는다. 재위임 없이 보조 최대 2개, 근거 있는 모델 상향은 작업당 한 번으로 제한한다. 자동 보고서는 기존 기록기로 생성한다. 설정 원본은 `codex/`의 비활성 템플릿이며 파일 존재만으로 현재 세션에 적용됐다고 보고하지 않는다.

## 함께 만드는 방식

- 사용자는 기획·코드·씬·UI·플레이 조정에도 직접 참여하는 제작 파트너다. 역할을 요청과 승인만으로 제한하지 않는다. 기존 대화에서 사용자가 원하는 참여 범위를 확인하고 필요한 분담만 함께 정한다.
- `사용자가 할 일 / AI가 맡은 일 / 함께 확인할 결과`를 나눈다. 프로젝트 시작을 승인받아도 사용자 작업까지 AI에게 위임됐다고 해석하지 않는다.
- 한 번에 함께 확인할 수 있는 작은 단위를 제안한다. 예: 발사 한 번의 조작감, 결과 화면의 재시작 흐름. 파일이나 함수마다 승인을 요구하지 않는다.
- 합의된 단위 안의 AI 작업은 끝까지 수행한다. 사용자 제작·플레이 의견에 달린 다음 단위는 그 결과를 받고 이어간다. 기다리는 동안 새 기능·에셋·전체 시스템을 앞서 만들지 않는다. 독립적으로 승인된 작은 작업만 계속한다.
- 작업 전 `이번 목표 / 분담 / 확인할 결과`, 결과 뒤 `확인된 것 / 바꿀 것 / 다음 한 단계`를 짧게 공유한다.
- 조사·병렬 에이전트·생성량은 현재 질문에 필요한 만큼만 사용한다. 역할표를 채우려고 에이전트를 늘리지 않는다. 기존 결과를 재사용하며 같은 조사·문서 전문 재작성·불필요한 재검사를 반복하지 않는다.
- 추가 조사나 제작 확대가 필요하면 무엇을 알아내거나 보여주기 위한 것인지 먼저 설명한다. 측정하지 않은 토큰 절약 수치를 만들지 않는다.

## 먼저 모드를 구분한다

| 사용자 의도 | 현재 수행 범위 | 프로젝트 쓰기 |
|---|---|---|
| 스킬/워크플로우 준비 | 스킬 설명서, 역할, 시퀀스, 문서 양식, 도구 검증 | 하지 않음 |
| 특정 프로젝트의 시작안 준비 | 목적·범위·프로젝트명·절대 경로·생성/재사용 방식을 검토표로 제시 | 하지 않음 |
| 식별된 프로젝트 시작 | 검토표의 대상과 범위에 대한 사용자 시작 결정 후 초기화·기획·제작 | 승인된 경로/범위만 |
| 이미 시작된 작업 계속 | 이전 시작 결정과 경로를 확인하고 현재 단계부터 진행 | 기존 승인 범위 |

“플로우를 만들자”, “스킬과 문서부터”, “시작하기 위한 준비”는 준비 모드다. 이때 종료 조건은 설명서·절차·양식·도구 검증이며 실제 프로젝트 생성이나 구현이 아니다. 새 폴더 생성, 기존 프로젝트에 문서 삽입, 씬 추가, 패키지 변경, 프로젝트 로그 초기화도 준비 요청만으로 수행하지 않는다.

유사 이름 프로젝트 발견이나 기획 A/B 선택은 대상 경로와 시작에 대한 승인이 아니다. 사용자가 이미 경로와 시작을 명시했다면 재승인을 요구하지 않는다. 시작 결정은 관련 메시지와 함께 기록하고 이후 매 단계 반복해서 묻지 않는다.

## 실행 계약

- 사용자가 이미 승인한 목표·범위·선택을 이어받는다. **식별된 프로젝트의 제작이 시작된 경우** 승인된 범위의 구현·검증까지 진행한다. 준비 모드에서는 문서와 흐름 자체를 완료한다.
- 비싼 미결정은 구체적인 검토안을 먼저 만든 뒤 사용자의 상황에 맞게 질문한다. 답을 기다리는 동안 기록 도구·조사·테스트 설계 등 독립 작업은 진행한다. AI 제안을 사용자 결정으로 승격하지 않는다.
- 여기서 자동 문서화는 **현재 작업 중인 에이전트가 단계 시작/종료와 변경·검증 직후 문서를 갱신하고 기록기를 실행하는 것**이다. 스킬 설치만으로 상주 감시·예약 실행·사용자의 Editor 조작 수집이 생기지 않는다.
- 결과는 한국어를 기본으로, 사용자 언어를 따른다. 작업 중인 프로젝트의 현재 씬·Prefab·Importer 설정은 보존한다.

## 0. 시작 검토와 대상 확인

준비 모드는 [시작 절차](references/startup-flow.md)까지만 수행한다. 사용자에게 목적, 새로 만들지/기존 프로젝트를 사용할지, 프로젝트명, **절대 경로**, 처음 만들/변경할 파일, 담당 역할, 첫 완료 기준을 제시한다. 경로 미정은 미정으로 표시한다. 시작 결정이 있어야 아래 초기화로 넘어간다.

## 프로젝트 시작 후: 현재 상태와 기록 시작

1. 시작 결정의 대상 프로젝트를 확인하고 적용되는 AGENTS, 기존 HANDOFF, 기획, manifest, 실제 변경 상태를 읽는다. 탐색으로 발견한 다른 프로젝트로 대상을 바꾸지 않는다. 새 프로젝트 생성이 승인됐다면 승인된 경로를 먼저 사용자에게 알리고 생성 결과 경로도 보고한다.
2. 기존 기획·기록 경로가 있으면 유지한다. 이 프로젝트에서 새 제작 기록이 필요하면 `Docs/Prototype/`와 `Docs/HANDOFF.md`를 사용한다. 지금 포함된 스킬 문서 배치는 사용자 요청으로 허용됐지만 게임 구현 시작 승인을 뜻하지 않는다. 기획 원본은 하나만 두고 다른 문서는 링크한다.
3. [문서 계약](references/documents.md)과 [에이전트 운영](references/orchestration.md)을 읽는다. 기록기를 처음 실행할 때 [기록 방법](references/recording.md)을 읽는다.
4. `scripts/workflow_log.py init --root <문서폴더>/evidence --title <프로젝트명>`을 실행한다. 이후 `record --event-file` 호출마다 REPORT.md가 갱신된다.
5. 최초 요청과 기존 결정의 출처를 기록한다. 기록 전 작업은 `retrospective` 메타데이터로 표시하고 시간을 소급 생성하지 않는다. 다음 실제 작업은 시작 이벤트를 먼저 남긴다.

## 1–6. 제작 시퀀스

| 단계 | 수행 | 다음 단계로 넘길 것 | 즉시 남길 문서/기록 |
|---|---|---|---|
| 1 요청 | 목표, 레퍼런스, 기한, 사용자 역할, 제약, 완료 기준을 구조화 | 사용자 확정과 미결정의 구분 | BRIEF, request 이벤트 |
| 2 기획 | 대표 플레이, 규칙, 피드백, 최소 범위, 검증 가설을 구체화 | 승인된 핵심 루프 또는 질문이 필요한 검토안 | 기존 GDD 또는 DESIGN, decision/checkpoint |
| 3 제작 제안 | 사람/AI 분담, 재사용, 작은 실행 단위와 완료 증거를 함께 정함 | 각자 맡은 작업과 함께 볼 결과 | PLAN, `stage: plan, kind: checkpoint` 이벤트 |
| 4 제작 | 사용자와 AI가 각자 맡은 범위를 제작하고 연결 | 실제 변경물과 사용자가 체험할 결과 | 변경 문서, start/finish, 파일 증거 |
| 5 리뷰 | 사용자의 플레이·제작 의견과 AI의 구조·검증 근거를 함께 검토 | 유지/수정/미실행과 다음 작업 단위 | REVIEW, review 이벤트 |
| 6 증명 | 요청→결정→구현→검증을 연결하고 다음 작업을 인계 | 보고서, 실행 결과 링크, 재개 지점 | REPORT 자동 생성, HANDOFF |

단계 4–5는 작업 단위마다 반복한다. 6단계에 와서 기록을 기억으로 복원하지 않는다. 매 단계 문서 담당이 증거를 받아 관련 문서만 갱신한다. 실제 구현 없이 문서만 있으면 기획/준비 단계라고 보고한다.

문서화는 AI가 담당하되 매 대화를 새 보고서로 늘리지 않는다. 결정·변경·검증·인계에 필요한 내용만 기존 문서에 반영한다. 함께 확인한 판단과 사람의 기여도 빠뜨리지 않는다.

## 기획·제작 연결

- 승인된 기획이 없으면 목적·대표 플레이·규칙·최소 범위·성공/실패 기준을 사용자와 정한다. `game-design-workshop`이 설치되어 있고 도움이 될 때만 활용한다. 설치되지 않아도 이 시작 검토표와 문서 계약으로 진행할 수 있다. 이미 결정된 항목을 다시 인터뷰하거나 면접 샘플을 상업 출시 기획으로 확장하지 않는다.
- 이미지 제작이 필요할 때만 설치된 `game-asset-pipeline`/`imagegen`으로 연결한다. 에셋 승인과 씬 수동 작업 보존 조건을 유지한다.
- Unity 프로젝트는 manifest에서 실제 버전·렌더 파이프라인·Luna 유무를 확인한다. ActiveAdStudio+Luna이면 현지 PlayableCore 재사용 지침을 적용한다. 다른 프로젝트에 해당 제약을 일반화하지 않는다.
- 외부 라이브러리 채택·세이브 포맷·코어 루프 등 되돌리기 비싼 선택은 기존 승인을 확인한다. 일상적인 파일명·기존 패턴 적용에는 별도 승인을 요구하지 않는다.
- 기존 Unity 씬 재생성·SaveAssets·SaveAndReimport 등을 검증 목적으로 무단 실행하지 않는다. 변경이 필요한 참조만 부분 수정하거나 별도 테스트 자산을 사용한다. 빌드/Editor 실행의 사용자 분담도 먼저 확인한다.

## 생산성 증거

- 기록 대상은 실제 납품 범위, 최초 실행 가능 빌드까지의 관측 경과시간, 변경 요청 처리시간, 재사용한 자산/코드, 본인과 AI의 작업 분담이다.
- 작업 단위의 start/finish는 같은 `task_id`로 연결한다. 병렬 작업 시간을 합쳐 전체 경과시간으로 보고하지 않는다. 대기/휴식이 포함되면 표시한다.
- 수동 작업 기준선 없이 절감률·배속·인건비를 만들지 않는다. 추정 작업시간과 관측시간을 분리한다. 최초 빌드는 실제 실행 증거가 확보된 시점에만 기록한다.
- 소스 생성, 정적 검사, Unity 컴파일, Play Mode, 기기 빌드를 구분한다. 코드 해시는 실행 성공이나 성능 향상의 증거가 아니다.
- 로그에는 요청의 필요한 요약과 산출물 경로를 남긴다. 인증정보, 사내 자료, 원본 전체 대화는 자동 수집하지 않는다.

## 매 작업 완료/인계 전

준비 모드에서는 프로젝트 문서를 새로 만들지 않는다. GUIDE·시작 검토 양식·역할 문서와 도구 검증 결과를 확인한 뒤, 설치된 스킬 위치와 아직 생성/시작되지 않은 범위를 설명한다. 아래는 프로젝트 시작 후에 적용한다.

1. PLAN의 작업 상태와 REVIEW의 검증 상태를 실제 결과에 맞춘다.
2. 결과 파일을 근거로 checkpoint/finish를 기록하고 자동 생성된 REPORT를 확인한다.
3. `verify --root ...`로 기록 파일의 변경/누락을 확인한다. 진행 중 수정은 새 checkpoint로 설명한다. 이전 증거를 지우지 않는다.
4. 설치된 `context-save`가 있으면 해당 규칙으로 기존 HANDOFF를 갱신한다. 없으면 문서 계약의 필수 내용을 기록한다.
5. 최종 답변은 완료물, 실제 검증, 미완료, 다음 행동을 짧게 연결한다. 기획 승인·사용자 Editor 작업이 남으면 그 항목만 구체적으로 전달한다.
