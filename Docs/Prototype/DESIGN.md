# A안 기획 원본

## 사용자 결정

[DECISION:user / R-002, R-011 / 2026-09-08] **Block 영역 클릭으로 목표 선택·발사 → 파괴 → 결과 → 재도전**, 그리고 **물리 비교**를 포함하는 A안으로 진행한다. 최초 요청의 ‘조준·발사’는 R-011에서 클릭이 조준을 겸하는 하나의 입력으로 구체화됐다. 별도 조준 단계는 없다.

이 루프 선택은 확정이다. 각 규칙과 한 번에 만들 분량은 아래처럼 분리한다.

## 확정 조작 — 클릭이 조준과 발사를 겸한다

[DECISION:user / R-011 / 2026-09-08] 출처: “조준은 따로 없고, Block이 있는 부분을 선택하면, 해당 위치로 공이 발사되어야해, 클릭이 조준인 셈이야. 그리고 Ball의 진행방향으로 Cannon이 돌아가야해”.

- 플레이어가 Block이 있는 영역을 클릭·선택하면 그 위치로 Ball을 발사한다.
- 클릭으로 목표 선택과 발사를 함께 처리한다. 별도의 조준 모드, 드래그 조준, 추가 발사 확인 입력은 이 조작에 포함하지 않는다.
- Cannon은 Ball의 진행 방향을 바라보도록 회전한다. 발사 방향과 대포가 바라보는 방향이 어긋나지 않아야 한다.

이 입력 규칙과 Cannon 회전은 사용자 확정 요구다. 다음 작업에서 조준·발사 방식의 채택 여부를 다시 질문하지 않는다. 실제 입력 API, 목표 월드 위치 계산, 발사 궤적·속도와 회전 연출은 이 요구를 만족하도록 아키텍처 이후의 제작 단위에서 구체화한다.

## 첫 확인 단위

[DECISION:user / R-011] 후속 첫 플레이 단위는 **Block 영역 클릭 → 선택 위치로 Ball 1개 발사·충돌**, 그리고 **Ball 진행 방향에 맞춘 Cannon 회전**이다. **Daniel의 구현 계획을 듣고 전체 아키텍처를 먼저 만드는 것이 선행 조건**이다. 현재 순서와 역할은 [PLAN](PLAN.md)에 둔다.

[HYPOTHESIS] 사용자가 원하는 방향으로 공을 보낼 수 있는지 먼저 확인하면, 파괴 연출·결과 화면을 만든 뒤 카메라와 입력을 다시 바꾸는 일을 줄일 수 있다. 아직 플레이로 확인하지 않았다.

위 가설은 아키텍처를 건너뛰고 기능부터 만들 근거가 아니다. AI가 곧바로 발사 기능을 구현하려 한 순서는 사용자 정정으로 철회했다.

## 미결정과 후속

- [DECISION:user / O-002] Unity 제공 Physics와 직접 구현 Physics를 비교한다. 사용자는 중앙 UpdateLoop 구독·분배 방식으로 과거 약 50% 레이턴시 개선 경험도 설명했다. 사용자 제공 과거 경험이며 현재 측정·재현 결과는 아니다.
- [OPEN] 물리 구현 비교와 개별/중앙 콜백 방식 비교의 조건·관찰 항목. 아키텍처 계획을 들은 뒤 설계한다.
- [CORRECTION / R-011] AI가 제시했던 드래그·놓기 입력과 별도 조준 단계는 현재 요구에 해당하지 않는다. 클릭 입력과 Cannon 회전은 위 확정 조작을 따른다.
- [OPEN] Block 영역의 선택 판정·목표 월드 위치 변환, 발사 속도·궤적, Cannon 회전 연출의 세부 값. 현재 카메라 구도와 사용자 Inspector 값은 보존하며 해당 제작 단위에서 조작감을 확인한다.
- [OPEN] 파괴 조건, 결과의 성공/실패 기준, 재도전 초기화 범위는 해당 작은 작업을 시작할 때 구체화한다.
- [PROPOSAL] 공/표적 한 종류와 기존 에셋으로 첫 조작을 검증한다. 공통 아키텍처는 [확정 기준](ARCHITECTURE.md)을 따르며, 이 조작 정정으로 새 외부 의존성이나 세이브 포맷을 정하지 않는다.

물리 성능·정확도·결정성의 우열은 아직 판단할 근거가 없다. 비교 설계를 정할 때 동일 시작 조건과 관찰 방법을 정의하고 실제 Unity 실행으로 확인한다.
